# Research: incident reproduction, chaos, and postmortem tooling

Purpose: decide which ideas fit KAVIRA's identity (**execution is the verdict**, **honest about what is reconstructed**, zero dependencies) and which do not.

Evidence labels: **[fetched]** the claim comes from a page fetched while writing this document (URL given). **[unverified]** the claim comes from the author's background knowledge and was not checked against a fetched page; treat it as a pointer, not a citation. Several vendor pages (Gremlin, Steadybit, AWS FIS, Honeycomb, Datadog, Sentry, k6, Locust, Pumba) were not fetched, so everything said about them is **[unverified]**.

## What others do, and how KAVIRA differs

| Tool | What it does | What KAVIRA lacks or does differently |
| --- | --- | --- |
| **Chaos Mesh** | Faults for runtime, network, filesystem and kernel, plus cloud APIs and physical machines; each fault is a Kubernetes custom resource (`NetworkChaos`), driven by UI, HTTP API or `kubectl`; Schedule, Workflow and StatusCheck resources orchestrate experiments. [fetched] <https://chaos-mesh.org/docs/> | Chaos tools inject faults into a **live system** to find unknown weaknesses. KAVIRA starts from a failure that **already happened** and reconstructs it in isolation. KAVIRA has no cluster integration and no fault catalog beyond four classes. |
| **LitmusChaos** | CNCF incubating chaos platform; declarative, tunable, schedulable experiments from ChaosHub; chainable in sequence or parallel; *probes* verify a steady-state hypothesis. [fetched] <https://litmuschaos.io/> | A probe asserting steady state is close to KAVIRA's regression test (`max_failures`, `max_p99_ms`). KAVIRA's assertion is derived from the incident, not authored up front. Whether Litmus reports a resilience score was **not** confirmed on the fetched page. |
| **Toxiproxy** | A proxy between app and dependency; toxics are latency (with jitter), bandwidth, slow_close, timeout, reset_peer, slicer, limit_data and packet_loss; "down" is disabling the proxy; scoped blocks apply and remove a toxic. [fetched] <https://github.com/Shopify/toxiproxy> | KAVIRA's network class is a tiny local-listener version of latency, loss, timeout and policy-deny. Missing: jitter, bandwidth caps, slicer, reset_peer, slow_close as named factors. These are cheap to add as one-factor arms. |
| **rr** (and Pernosco) | rr records a Linux program once and replays it deterministically, with reverse execution under gdb; it has a "chaos mode" for intermittent bugs, but the fetched page does not say how it works. [fetched] <https://rr-project.org/> Pernosco as a hosted debugger over rr recordings is **[unverified]**. | Record-replay is *exact*. KAVIRA states the opposite on purpose: `exact_replay` is always false. The useful idea to borrow is not replay but **flakiness amplification**: rr's chaos mode exists because one run is weak evidence. |
| **Tracetest** (trace-based testing) | Uses OpenTelemetry traces as test specs: select spans, assert on attributes or timing, wildcards over categories, YAML or UI. [fetched] <https://docs.tracetest.io/> | KAVIRA takes a hand-written evidence bundle, not traces. Ingesting a trace (span durations, error spans) as a bundle source would remove the manual capture step. Large effort, and span data raises its own honesty question (what a trace does not contain). |
| **Jepsen** | Open-source library and published analyses testing whether distributed databases, queues and consensus systems meet their documented claims; Elle is a named checker. [fetched] <https://jepsen.io/> The mechanism (record a concurrent history, then check it against a model) is **[unverified]** from this page. | KAVIRA has no concurrent histories and no consistency model, so a Jepsen-style checker is out of scope. The transferable idea is "a verdict is a *checker over a recorded run*", which KAVIRA already does with the runner. |
| **Google SRE postmortem culture** | A postmortem records the incident, impact, mitigation, root cause(s) and follow-ups, with metadata for automated analysis; blameless: contributing causes without indicting people, assume good intent, fix systems not people. The page points to a separate example template rather than listing section headings. [fetched] <https://sre.google/sre-book/postmortem-culture/> | KAVIRA produced a repair package but no narrative. A generated draft that keeps *demonstrated*, *captured* and *hypothesis* apart is a natural fit. |
| **Delta debugging (ddmin)** | Zeller and Hildebrandt's algorithm reduces a failing input by testing subsets and complements, raising granularity when no chunk can go; result is 1-minimal; worst case O(n^2) tests. The paper PDF could not be read by the fetch tool, so these points are **[unverified]** background knowledge. Paper: <https://www.cs.purdue.edu/homes/xyzhang/fall07/Papers/delta-debugging.pdf> | KAVIRA had no reduction step: a bundle with six changed config keys reported "the config regressed" without saying which keys matter. |
| **Flaky-test bisection and reruns** (Meta, Google research) | Repeated runs and statistical treatment of flaky tests. Not fetched. **[unverified]** | KAVIRA reported a single yes/no per compile, which is exactly the failure mode flaky-test research warns about. |
| **Gremlin, Steadybit, AWS FIS, Pumba** | Commercial or cloud fault injection against live infrastructure or containers. Not fetched. **[unverified]** | Same category as Chaos Mesh: live fault injection, not incident reconstruction. No new KAVIRA idea beyond the fault catalog. |
| **k6, Locust** (load with fault injection) | Load generators; k6 has an extension ecosystem for faults. Not fetched. **[unverified]** | KAVIRA's workload is a bounded stand-in, not a load test. A load *profile* (requests, size) is already minimizable. |
| **Honeycomb / Datadog incident timelines, Sentry replay** | Timelines and session replay built from production telemetry. Not fetched. **[unverified]** | KAVIRA does not collect telemetry. It accepts a hand-supplied `timeline` and labels it captured. |

## Ranked ideas

Ranking criteria: (1) strengthens "execution is the verdict", (2) cannot be made to overclaim, (3) works on the four existing classes without new dependencies, (4) effort.

1. **Confidence and flakiness estimation (built).** One verdict is one sample. Repeat the whole pipeline and report the rate with a Wilson score interval; allow `not_reproduced` only after enough clean runs. Rationale: it is the cheapest way to remove luck, and it is purely a stronger form of execution. Sources: rr's chaos mode exists for the same reason (rr-project.org, fetched); flaky-test literature **[unverified]**. Deliberately no random seed: the runners contain no random source, so a seed would fake control over wall-clock timing.
2. **Delta-debugging minimizer (built).** Shrink the config diff, network factors, or workload requests to the smallest input that still fails, using the runner as the oracle. Rationale: turns "the config regressed" into "these two keys are needed". Honest limit: 1-minimal, not global minimum, and sufficient-in-reconstruction is not cause-in-production. Source: Zeller and Hildebrandt (background **[unverified]**, paper URL above).
3. **Postmortem draft export (built).** Blameless Markdown following the SRE sections, with `Demonstrated`, `Captured` and `Hypothesis` kept apart and a "Not established" section. Source: sre.google postmortem culture (fetched). Timeline comes from an optional bundle field, never invented.
4. **Before/after regression export (built).** A POSIX `regress.sh` that fails on the captured condition and passes on the repair, using only the kavira binary. Rationale: a regression test that cannot fail before the fix proves nothing; this checks both sides. Related: LitmusChaos probes as steady-state assertions (fetched).
5. **More one-factor network arms** (jitter, bandwidth, reset_peer, slow_close, from Toxiproxy's toxic list, fetched). Low effort, extends an existing class. Not built.
6. **New incident classes** (DNS failure, certificate expiry, connection-pool exhaustion, retry storm). Each needs a runner template, hypotheses, repair arms, fixtures equal to `examples/`, and e2e coverage. Real value, but each is a feature of its own size; the four built features above apply to every class automatically. Not built.
7. **Trace-to-bundle ingestion** (Tracetest, OpenTelemetry). Removes manual capture, but needs a trace schema, and traces omit the very conditions KAVIRA reconstructs. Not built.
8. **Record-replay (rr/Pernosco style).** Rejected: it contradicts the "never claim exact replay" boundary and needs process-level instrumentation.
9. **Jepsen-style history checking.** Rejected: needs concurrent histories and a consistency model; out of scope for four resource and config classes.
10. **Live fault injection (Chaos Mesh, Gremlin, FIS).** Rejected: KAVIRA is local-first and isolated by design; it must not touch production.

## Chosen and rejected, in one line each

- Built: confidence (`kavira repeat`), minimizer (`kavira minimize`), postmortem draft (`kavira postmortem`), regression export (`kavira export`).
- Not built: new incident classes (size), network arms (follow-up), trace ingestion (schema), record-replay (boundary), Jepsen checking (scope), live injection (boundary).
